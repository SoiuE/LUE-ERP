# 用户与角色管理改进需求

版本：v0.1（待确认）
日期：2026-10-17
状态：已确认，按本需求实施

## 1. 背景与现状

当前后台已有“用户管理”和“角色与权限”入口。用户列表从角色数据读取用户角色，创建用户时前端角色选项却是固定写死的 `ADMIN`、`OPERATOR`、`VIEWER`；系统初始化的角色还包含 `WAREHOUSE`。因此角色维护信息与新建用户可选项可能不一致，新增角色也无法自动出现在用户创建表单中。

现有用户列表展示启用状态，但缺少禁用/启用操作和重置密码入口。认证逻辑会拒绝已禁用用户登录。

## 2. 本次目标

1. 用户新建和角色权限管理使用同一份系统角色数据，避免角色选项与实际角色不匹配。
2. 获授权的管理人员可以重置用户密码。
3. 获授权的管理人员可以禁用或重新启用用户，并清晰查看用户状态。
4. 用户管理相关操作具有明确的权限控制、结果反馈和操作留痕。

## 3. 功能需求

### 3.1 统一角色数据

- 新建用户表单中的角色选项应由系统角色列表动态加载，不再维护独立的固定角色清单。
- 选项至少展示角色名称；如角色名称重复或需要辨识，可同时显示角色编码。
- 用户列表中的角色名称/编码应与角色管理页面显示的数据保持一致。
- 角色列表加载失败时，应提示错误并阻止提交无效角色；加载中应显示等待状态。
- 新建用户提交的角色必须在服务端再次校验为有效角色，不能仅依赖前端选项限制。
- 对已停用或不可分配角色的处理规则应与角色管理既有规则一致；如当前没有“角色停用”能力，则不新增该能力。

### 3.2 重置用户密码

- 用户管理列表为每个用户提供“重置密码”操作。
- 操作前要求管理员输入并确认新密码，密码规则与新建用户一致（至少 8 位，最多 100 位）。
- 提交成功后更新密码摘要，不得以明文保存或在列表、日志中回显密码。
- 页面应反馈成功或失败；重复点击期间应防止重复提交。
- 重置密码应记录操作人、目标用户、操作类型和时间，不记录密码内容。
- 管理员可以重置其他用户密码；是否允许重置自己的密码沿用同一权限控制，并在确认需求后按实现方案执行。

### 3.3 禁用与重新启用用户

- 用户列表提供启用/禁用操作，并清楚显示当前状态。
- 禁用操作需要二次确认，确认信息应包含目标用户名；成功后列表状态立即更新。
- 已禁用用户不能新建登录会话；重新启用后可按正常认证流程登录。
- 禁用操作应记录操作人、目标用户、操作类型和时间。
- 不允许通过误操作禁用当前正在操作的唯一有效系统管理员账户；当目标会导致系统没有任何可用管理员时，应拒绝操作并给出明确原因。
- 对已登录用户禁用后的既有会话失效时点需明确：建议禁用后其后续请求立即失效；若现有令牌机制无法即时撤销，应在确认后选定兼容方案。
- 重新启用操作无需额外确认（如需保持一致，可改为启停均确认）。

### 3.4 权限与审计

- 查看用户、重置密码、启停用户的权限应由后端校验，前端隐藏/禁用操作入口不能代替服务端授权。
- 延用现有“用户管理”查看权限和“用户维护”管理权限，除非实施时发现需拆分更细权限并经确认。
- 创建用户、重置密码、禁用和启用均写入操作日志，日志不得包含密码或密码摘要。
- 未授权请求应失败，且不得更改用户数据。

## 4. 页面与交互

- 用户列表角色列应支持多角色展示（若系统允许用户具有多个角色），避免数据库关联结果造成同一用户重复显示。
- 状态标签分别显示“启用”和“禁用”，颜色表达应一致。
- 操作列提供重置密码、禁用/启用入口；不可执行的操作应隐藏或明确禁用并说明原因。
- 新建用户弹窗从角色列表加载选项；默认角色应为有效且可分配的角色，不能假定固定存在 `OPERATOR`。
- 操作失败时保留必要输入（密码字段除外），并显示可理解的错误提示。

## 5. 验收标准

1. 在角色列表中存在 `WAREHOUSE` 等非原先写死的角色时，新建用户表单可选择该角色，并成功创建对应用户。
2. 新增有效角色后，无需修改前端固定选项即可在新建用户页面选择该角色。
3. 服务端拒绝不存在的角色编码，用户记录及角色关联不发生部分写入。
4. 管理员重置密码后，用户可使用新密码登录，旧密码不可登录；密码不出现在接口响应或操作日志中。
5. 禁用用户后，该用户无法登录；重新启用后可再次登录。
6. 无管理权限的用户不能通过直接调用接口重置密码或启停账户。
7. 禁用唯一有效管理员的请求被拒绝；至少保留一个可用管理员账户。
8. 用户启停与密码重置均留下可追溯的操作日志，且不会记录密码内容。
9. 用户列表不会因角色关联产生同一用户多行，角色名称、编码和状态显示正确。

## 6. 范围外

- 本需求不包含角色新增、编辑、删除或权限勾选管理功能。
- 本需求不包含用户资料编辑、批量导入、批量启停或自助找回密码。
- 本需求不包含密码复杂度策略升级、强制定期换密或密码历史校验。
- 本阶段仅编写需求文档；程序修改待需求确认后进行。

## 7. 待确认事项

1. 重置密码是否统一由管理员输入新密码，还是系统生成临时密码？本草案按管理员手动设置处理。
2. 重置当前登录用户自己的密码是否允许？本草案将其纳入管理员重置流程。
3. 禁用用户后是否要求其所有已登录会话立即失效？本草案建议立即失效。
4. 若被禁用用户是最后一个有效管理员，应始终阻止禁用；是否允许系统仅有一个管理员但其本身操作禁用其他管理员？本草案要求任何情况下至少保留一个有效管理员。
