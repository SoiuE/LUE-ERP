# 以图搜商品准确度优化方案

日期：2026-10-20

## 目标与原则

当前方案以 OpenCLIP `ViT-B-32 / laion2b_s34b_b79k` 提取 512 维向量，再用余弦相似度检索 SQLite/NumPy 索引；Spring 后端合并同一 SKU/货品的多图，按最高相似度排序并返回最多 10 个对象。准确度优化应先用真实查询集找出错因，再调整图片数据、预处理、模型和排序。向量库负责存取和排序，换向量数据库本身不会修复模型无法区分相似商品的问题。

优化过程中保持“查询结果只是候选、确认前不改业务数据”的边界。任何模型或预处理变更都要增加模型/预处理版本并重建索引，禁止把不同版本的向量混在同一索引中。

## 一、先建立可复现的准确率基线

### 查询集

从真实使用场景收集经授权的查询照片，并由业务人员标注正确 SKU 或仓库货品。覆盖：

- 手机近拍、斜拍、远拍、局部遮挡、不同光线和背景。
- 白底商品图、实物照片、包装图，以及系统中常见的图片分辨率和压缩质量。
- 外形相近但型号、颜色、尺寸、配件不同的难区分商品。
- 查询对象没有入库图片、图库没有对应商品、图片模糊或无法辨认等拒识场景。

同一商品的近重复图片、同一次拍摄的裁剪图不能同时出现在调参集和最终验收集。建议按 SKU 分组切分，先用约 70% SKU 调试，约 30% SKU 做冻结验收；SKU 数量较少时由业务人员另留一批从未参与调参的商品。另设真实线上反馈集，版本化并记录查询图哈希、标签、时间、模型版本和索引版本；只有获得授权后才保留查询图本身。

### 指标与错误分类

每次实验记录：

- `Recall@1`、`Recall@5`、`Recall@10`：正确商品是否出现在前 N 名。
- `MRR` 或 `NDCG@10`：正确结果排位是否靠前。
- 未命中率、错误候选率，以及按商品类别、图片来源、拍摄场景拆分的结果。
- 查询延迟、CPU/内存占用和索引更新时间。

人工复核错误样本并标注主因：图库缺少正确角度、图片关联错误、商品本身难区分、查询图质量差、模型召回不足、阈值拒绝正确商品或排序不佳。准确率汇总必须与冻结验收集一起报告，不能只报告调参集成绩。

## 二、按收益和成本分阶段优化

| 阶段 | 做法 | 验收重点 |
|---|---|---|
| 0. 数据质量 | 补齐每个 SKU/货品的主图与实拍图；优先覆盖前景清晰、不同角度、颜色/尺寸差异明显的图片；修正错误关联和重复资产；排除现场作业照片；检查失败和未索引资产。 | 正确商品的可用索引覆盖率；重复/错误关联数；队列失败率。 |
| 1. 建立基准 | 构造并冻结标注查询集，跑当前模型，按上述指标和错误类型分组。 | 得到可重复的基准结果和主要错误清单。 |
| 2. 低成本预处理 | 使用 EXIF 方向校正；保留合理长宽比后按模型规格缩放；对明显背景干扰、留白过多或商品过小的图像尝试商品主体裁剪。对原图和裁剪图分别建向量或在查询时做多视图查询，比较而后选择。 | 分场景 Recall@K 提升，且不显著增加误召回和延迟。 |
| 3. 候选重排 | 先用当前向量召回较大的候选集（如 50–100 张图片），再对高相似候选做更精细的局部/高分辨率特征比较；汇总到对象时可评估“最高分”与“最高分加多图支持”两种规则。 | 冻结集 NDCG@10/MRR 提升；端到端延迟可接受。 |
| 4. 模型对比 | 在相同冻结数据、预处理、候选集和硬件上对比当前模型、OpenCLIP `ViT-B-16` 与 SigLIP 2 的适配尺寸；模型是否更好以商品检索数据实测为准。 | Recall@K、排序指标、推理延迟、内存、模型文件大小及部署可行性。 |
| 5. 领域微调 | 有足够标注后，用同商品不同视角/场景构造正样本，用同类近似但 SKU 不同的商品构造 hard negatives，微调图像编码器或轻量投影层；使用留出的 SKU/查询集防止记忆训练商品。 | 冻结集持续优于未微调基线；未出现类别/场景退化。 |

阶段 0–3 通常比直接训练模型更值得先做：缺少真实商品图、关联错误和拍摄角度单一会直接限制可达到的准确率。

## 三、模型与排序建议

1. **先保留当前模型作为基线。** OpenCLIP 官方仓库列出了不同骨干网络和预训练权重，但通用数据集成绩不能代替本项目商品图检索成绩。
2. **只做小规模候选对比。** 推荐先测 `ViT-B-16`，再测 SigLIP 2 的 B 级或可部署尺寸；不要一开始就上大型模型。SigLIP 2 论文报告了其在图文检索和视觉表征上的改进，但这不保证对本 ERP 的细粒度 SKU 区分一定更准确。
3. **hard negatives 优先选择“同类近似不同 SKU”。** 如颜色相近但型号不同、同款不同尺寸、单品与套装、商品与配件。这类样本能直接暴露业务需要模型学会的差别。
4. **校准低相似度阈值。** 当前后端使用全局 `minimum-score`（默认 0.20）。在验证集上绘制阈值与正确召回/错误候选的关系；必要时按商品类别设置阈值，保留“无可靠候选”的拒识结果，不要单纯降低阈值追求结果数量。
5. **对象聚合规则也需验证。** 当前对象多图取最高图片分。可测试多图中有多个高分支持时加分的规则，但需防止图片数量多的对象获得不公平优势。
6. **文本与条码作为辅助信号。** 若查询图能可靠识别条码或商品文字，可把 OCR/条码结果作为二次过滤或加权证据；视觉分数仍保留，OCR 失败不能阻断纯图片检索。不要把 OCR 作为第一阶段必需依赖。

## 四、索引、版本和发布

每次模型或预处理版本至少记录：模型架构、预训练权重/文件校验和、向量维数、图片预处理参数、阈值版本和索引创建时间。构建新模型索引时先写入独立版本索引，抽样检查向量数、失败资产和候选结果，再切换服务使用版本；保留旧索引/备份以便回滚。完成切换后再观察线上反馈，确定稳定后清理旧版本。

全量重建前后核对：符合条件资产数、`INDEXED`/`FAILED` 数、模型版本一致性、样本 SKU 检索结果和服务健康状态。若改用不同维数模型，必须创建新索引，不能复用 SQLite 中的旧向量。

## 五、建议的第一轮执行清单

1. 等图片搜索服务和当前模型正常运行，确认当前商品索引能完整建立。
2. 选取 30–50 个有代表性的 SKU/货品，收集每个对象至少 3 类图片（标准图、实物角度、难例/相似款）；另准备至少 100 张带正确对象标签的查询图。若实际规模较小则覆盖全部主要商品，并注明样本不足的类别。
3. 固定一批不参与调参的 SKU 做验收，先测 `Recall@1/5/10` 和错误类型。
4. 先修图、补图、修关联，再比较主体裁剪与多视图方案。
5. 在同一验收集上比较 B/32、B/16 和 SigLIP 2 适配尺寸，记录准确度与 CPU 延迟。
6. 只对确定的改进方案开新版本索引，离线抽测后再切换；若没有稳定提升则维持当前模型。
7. 累积足够高质量 hard-negative 数据后，再安排领域微调实验。
