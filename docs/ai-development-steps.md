# AI 开发执行步骤

版本：v0.2
日期：2026-10-14
适用范围：后续 AI 编程开发指令基线

## 1. 开发原则

后续 AI 开发时，应严格遵循以下原则：

- 先实现可运行的 MVP，再逐步增强。
- 第一版不接入速卖通官方 API。
- 第一版以 Excel 导入为主要数据入口。
- 【本次新增】平台侧先完成 JIT 组包/预约和仓发备货组包/预约；用户将平台导出的 `.xlsx` 表格直接导入 ERP，由 ERP 解析和校验。无需 Python 转换程序；ERP 不重复执行平台组包或预约。
- 【本次新增】必须区分 WAREHOUSE 客户销售汇总与速卖通仓发入平台仓备货单：前者不扣本地库存，后者本地实际发货确认时扣减本地库存。
- 【本次新增】仓发备货缺货可关联采购单；采购入库后继续拣货。平台预约与 ERP 本地作业状态分开保存，重复导入不得覆盖已完成本地操作。
- 所有外部数据必须经过导入批次和原始数据记录。
- 内部 SKU 是系统的核心经营主键。
- 任何库存、包材库存变化都必须生成流水。
- 手机端仓库操作与 PC 端共用同一套后端库存、包材、采购和权限规则。
- 爬虫和 RPA 只做框架预留，不在第一版实现具体采集。
- 代码结构要为后续多平台扩展预留 platform 字段和数据源类型。
- 开发环境与最终运行环境分离；开发者不必接入目标局域网，地址和凭据通过环境配置提供，不写死在代码中。
- 最终部署目标为企业局域网内服务器；正式配置只开放 Web 访问端口，数据库、Redis 和 MinIO 限制在服务器或容器内部访问。

## 2. 推荐项目结构

建议采用前后端分离：

```text
LUE ERP/
  docs/
  backend/
  frontend/
  image-service/
  deploy/
  data-templates/
```

目录说明：

- docs：需求、设计和开发说明。
- backend：Spring Boot 后端。
- frontend：Vue 3 前端。
- image-service：图片搜索服务，后续实现。
- deploy：Docker Compose、Nginx、部署脚本。
- data-templates：Excel 导入模板。
- frontend 内建议同时包含 PC 路由和 mobile 路由，第一版手机端使用 H5/PWA，不做原生 App。

## 3. 开发阶段总览

### 阶段 0：工程初始化

目标：

- 创建前后端工程。
- 创建基础部署文件。
- 创建数据库迁移机制。

任务：

- 初始化 backend Spring Boot 项目。
- 初始化 frontend Vue 3 项目。
- 配置 MySQL、Redis、MinIO 的 Docker Compose。
- Compose 用于开发机本地依赖及部署验证，不要求开发机位于最终部署局域网；开发、测试、正式环境的连接地址通过配置区分。
- 配置后端数据库连接。
- 配置统一异常处理、统一响应结构、日志。
- 配置基础代码风格和 README。

验收：

- 前端能启动。
- 后端能启动。
- 后端能连接 MySQL。
- Docker Compose 能启动 MySQL、Redis、MinIO。
- 所有本地服务地址均可配置，阶段 0 不依赖接入最终部署局域网，也不包含正式环境固定 IP 或真实凭据。

### 阶段 15：【本次新增】速卖通表格传输与本地发货履约

目标：

- 接收速卖通平台已完成组包和预约的数据，并在 ERP 完成本地拣货、缺货采购、实物打包和交接发货。

必须遵守：

- 第一版由 ERP 页面直接接收平台导出的 `.xlsx` 表格，解析中英文表头、校验字段并显示错误回执；不需要 Python 转换程序，不接入速卖通官方 API，不自动化抓取平台页面。
- 速卖通平台负责 JIT 订单组包/预约及仓发入平台仓备货单组包/预约；ERP 导入其结果，不再次创建或变更平台组包和预约。
- 订单/销量汇总 `order_summaries` 只用于销售统计和利润，不直接作为完整履约订单头/行。
- WAREHOUSE 客户销售订单不扣减本地商品库存；仓发入平台仓备货单属于独立本地备货出库，实际发货确认时扣减本地库存。
- JIT 订单支持分批发货；同一订单的所有批次固定使用一个发货仓库，累计实发不得超过订单明细数量。
- 仓发备货单支持缺货采购、采购入库后续拣；两类来源单据均需可追溯库存流水。
- 首期使用默认逻辑仓库承接现有本地库存，不进行实物仓库迁移；数据归属转换不得改变库存总量。
- 使用平台稳定单据 ID、订单行 ID、组包批次 ID、包裹/箱号及预约编号建立关联；无稳定明细 ID 且无法可靠生成辅助键时进入人工核对，不得静默合并。
- 平台状态与 ERP 本地作业状态分开保存；重复导入必须幂等，不得重复创建发货单或库存流水，也不得回退已完成的本地状态。
- 所有商品/包材库存变化通过业务单据和流水完成；缺货、预约临期和数据不匹配需提示并可追踪。

任务：

- 定义 JIT 组包预约表、仓发备货组包预约表两类导入字段和填写说明；支持直接上传平台导出的表格。
- 实现 ERP Excel 解析与校验，保留源文件、批次号、原始行和错误回执。
- 实现平台订单/仓发单外部 ID 与 ERP 单据的关联模型和导入幂等规则。
- 实现 JIT 本地发货单、明细、包裹关系及部分发货。
- 实现仓发入平台仓备货单、明细、包裹关系、缺货采购关联和预约信息。
- 实现按组包批次查询、SKU 汇总拣货、扫码校验、实发确认和异常提醒。
- 将发货确认关联到库存流水和包材流水；订单行累计实发不得超量。
- PC 和手机端展示平台来源单号、组包/包裹信息、预约时间及本地履约进度。

验收：

- 可直接导入平台导出的 JIT 组包预约表和仓发备货表，并分别执行对应校验。
- ERP 能区分 JIT 客户订单、WAREHOUSE 客户销售汇总和仓发入平台仓备货单。
- 重复导入不重复创建本地发货记录或库存流水；SKU 未匹配数据可修复后重处理。
- JIT 可分批发货且仓库固定；剩余数量计算正确。
- 仓发备货缺货可关联采购，采购入库后继续拣货；确认发往平台仓后本地库存扣减并生成流水。
- 首期可在默认逻辑仓库完成作业，现有库存归属初始化不改变库存总量，也不要求实物搬仓。
- WAREHOUSE 客户销售汇总不会触发本地商品库存扣减。
- 平台组包/预约信息可查询，本地履约进度不会被平台文件重置。
- 库存流水可追溯到 ERP 发货单、明细和平台来源单号。

## 4. 建议数据库枚举

### 4.1 平台 platform

```text
ALIEXPRESS
TEMU
TIKTOK
SHOPEE
OTHER
```

第一版只使用 ALIEXPRESS。

### 4.2 数据源类型 source_type

```text
MANUAL
EXCEL
CRAWLER
RPA
API
```

第一版主要使用 EXCEL 和 MANUAL。

### 4.3 订单模式 order_mode

```text
JIT
WAREHOUSE
```

WAREHOUSE 表示客户销售的仓发模式，该类销售汇总不扣本地商品库存。速卖通仓发入平台仓备货单是独立来源单据，本地发货确认时扣减本地库存。平台组包和预约在速卖通完成后，用户直接把平台导出的表格导入 ERP。

### 4.4 导入状态 import_status

```text
PENDING
VALIDATING
FAILED
SUCCESS
PARTIAL_SUCCESS
```

### 4.5 任务状态 task_status

```text
PENDING
RUNNING
SUCCESS
FAILED
NEED_MANUAL
CANCELLED
```

## 5. API 设计原则

后端 API 建议遵循 REST 风格：

```text
GET    /api/shops
POST   /api/shops
PUT    /api/shops/{id}
DELETE /api/shops/{id}

GET    /api/skus
POST   /api/skus
PUT    /api/skus/{id}

POST   /api/import-batches
POST   /api/import-batches/{id}/preview
POST   /api/import-batches/{id}/commit

GET    /api/orders
GET    /api/inventory/stocks
POST   /api/inventory/inbound
POST   /api/inventory/outbound

GET    /api/profits/sku-daily
```

统一响应结构建议：

```json
{
  "success": true,
  "code": "OK",
  "message": "",
  "data": {}
}
```

统一分页结构建议：

```json
{
  "items": [],
  "page": 1,
  "pageSize": 20,
  "total": 0
}
```

```text
请基于 docs/requirements.md 和 docs/ai-development-steps.md 开发【模块名称】。

目标：
- ...

范围：
- ...

验收：
- ...

限制：
- 不接入官方 API。
- 保持 Excel 导入框架。
```

- 完成后运行测试或启动校验。
- 在回复中说明变更文件、验证结果和未完成事项。
